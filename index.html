1. Overview

This test script writes sample data to each type of browser storage and ties every write to a OneTrust consent category. That makes it easy to check whether the CMP blocks and allows each one correctly.

Summary

A helper script loads first and is never blocked. It defines three reusable functions: one sets cookies with a one-year expiry and the SameSite and Secure attributes, one writes to localStorage or sessionStorage and catches errors so a blocked storage doesn't stop the page, and one adds a record to IndexedDB and then closes the connection so the database can be deleted later.

The writes themselves are split into four script blocks, one per consent category. Each block is set to type="text/plain", so it only runs once the user consents to its category:

  • Performance (C0002) sets PerformanceCookie and saves PerformanceLocal in localStorage.
  • Functional (C0003) sets FunctionalCookie and saves FunctionalSession in sessionStorage, which is cleared when the tab closes.
  • Targeting (C0004) sets TargetingCookie, saves TargetingLocal as a JSON object in localStorage, and adds a record to the TestDB IndexedDB database.
  • Social Media (C0005) sets SocialCookie and adds a test entry to the test-cache-v1 Cache Storage.

A final, unblocked script registers an optional Service Worker (/sw.js). If the file is missing, it logs a warning instead of failing silently.

Consent only decides whether each block runs. Data that has already been written stays in the browser after the user withdraws consent and has to be removed separately, for example with the clear-storage script.

What each category writes
Category Cookie Web Storage IndexedDB Cache Storage
C0002 Performance PerformanceCookie localStorage PerformanceLocal — —
C0003 Functional FunctionalCookie sessionStorage FunctionalSession — —
C0004 Targeting TargetingCookie localStorage TargetingLocal (JSON) TestDB → TrackingStore —
C0005 Social Media SocialCookie — — test-cache-v1

2. How consent blocking works

What it is. Browsers only execute a <script> whose type is a JavaScript MIME type (or is empty). Any other value, such as text/plain, makes the browser treat the block as inert data. OneTrust uses this behaviour for JavaScript type rewriting, its recommended manual blocking method: you mark a script as text/plain and add a class naming its category, and OneTrust switches it to an executable type once that category has consent.

<!-- Normal script: runs immediately -->
<script type="text/javascript"> code </script>

<!-- Blocked until Performance (C0002) is allowed -->
<script type="text/plain" class="optanon-category-C0002"> code </script>

<!-- External file, same pattern -->
<script type="text/plain" class="optanon-category-C0004" src="/js/ads.js"></script>

<!-- Needs several categories: all must be allowed -->
<script type="text/plain" class="optanon-category-C0002-C0004"> code </script>

Default category IDs

ID Category Typical examples
C0001 Strictly Necessary Session, load balancing, consent cookie itself
C0002 Performance Analytics, e.g. Google Analytics
C0003 Functional Language selection, chat widgets
C0004 Targeting Advertising, remarketing pixels
C0005 Social Media Share buttons, embedded social content
Key point: a CMP can't block a cookie or storage write directly. It blocks the script that performs the write. Any write placed outside a blocked script, for example in the helper block, runs regardless of consent.

Use cases

  • Hard-coded inline scripts that Auto-Blocking doesn't recognise.
  • First-party custom scripts that write to localStorage, IndexedDB or Cache Storage.
  • Testing that each category is enforced on its own before a production rollout.

Don't combine manual blocking and Auto-Blocking on the same script. Use one method per source.

3. The helper script

The helper block only defines functions and stores nothing, so it can safely run without consent. Its functions are global, so the category blocks can call them once OneTrust unblocks them.

Function What it does Why it's built this way
isHttps Checks location.protocol Lets Secure be added only on HTTPS, so the test still works on http://localhost.
setCookie() Writes a cookie with path=/, a one-year max-age, SameSite=Lax and conditional Secure Encodes the value with encodeURIComponent so semicolons, commas or spaces can't break the cookie string.
safeStorage() Writes to localStorage or sessionStorage inside try/catch Storage can throw (quota full, or storage disabled by settings or privacy mode). Catching the error keeps the rest of the page running. Objects are converted with JSON.stringify because Web Storage only stores strings.
writeIndexedDB() Opens a database, creates the store on first run, writes one record and closes the connection An open connection blocks indexedDB.deleteDatabase(). Closing it lets the clear-storage script delete the database.

4. Cookies

C0002C0003C0004C0005

What it is. A cookie is a small name–value pair the browser stores and automatically sends to the server with matching HTTP requests. Servers set cookies with the Set-Cookie response header. Scripts read and write them through document.cookie, which acts as a getter and setter. Each assignment sets or updates only one cookie.

Attributes used in the test

Attribute Meaning Value in test
path URL path the cookie applies to. / means the whole site. /
max-age Lifetime in seconds, relative to now. Takes precedence over expires. Without either, the cookie is a session cookie and is removed when the browser closes. 31536000 (one year)
SameSite Controls whether the cookie is sent on cross-site requests. Strict sends it only in same-site contexts. Lax also sends it on top-level navigations to the site. None sends it everywhere and requires Secure. Lax
Secure Only sent over HTTPS. Added on HTTPS only
domain Host the cookie is sent to. If omitted, it's the current host only, with no subdomains. If set, subdomains are included. Omitted (host-only)
HttpOnly Hides the cookie from JavaScript. It can only be set by the server, not through document.cookie. Not used

Examples

// Set
document.cookie = "theme=dark; path=/; max-age=2592000; SameSite=Lax; Secure";

// Read one cookie
const theme = document.cookie.split("; ").find(c => c.startsWith("theme="))?.split("=")[1];

// Delete: same name, path and domain, with max-age=0
document.cookie = "theme=; path=/; max-age=0";

// Server-side equivalent
Set-Cookie: theme=dark; Path=/; Max-Age=2592000; SameSite=Lax; Secure

Use cases

  • Session and login state (usually HttpOnly, set by the server).
  • Analytics identifiers such as _ga (Performance).
  • Language or region preference (Functional).
  • Advertising and remarketing IDs (Targeting).
  • Storing the consent decision itself, for example OneTrust's OptanonConsent.
Testing tip: to delete a cookie, you must match its path and domain exactly. A cookie set with domain=.example.com won't be removed by a delete that omits the domain. This is a common reason cookies "survive" consent withdrawal.

5. localStorage and sessionStorage (Web Storage API)

C0002C0003C0004

What it is. Web Storage is a simple, synchronous key–value store of strings, scoped to the page's origin (scheme + host + port). Unlike cookies, its data is never sent to the server automatically. Browsers typically allow around 5 MB per origin.

localStorage sessionStorage
Lifetime Persists until cleared by script or user Cleared when the tab or window closes
Scope Shared by all tabs on the same origin Per tab and per origin
Used in test for PerformanceLocal, TargetingLocal FunctionalSession

Examples

localStorage.setItem("PerformanceLocal", "Performance localStorage!");
localStorage.getItem("PerformanceLocal");         // "Performance localStorage!"

// Objects must be serialised
localStorage.setItem("TargetingLocal", JSON.stringify({ id: 123, consent: true }));
JSON.parse(localStorage.getItem("TargetingLocal")).id; // 123

sessionStorage.setItem("FunctionalSession", "Functional sessionStorage!");
localStorage.removeItem("PerformanceLocal");      // delete one key
localStorage.clear();                             // delete everything for this origin

Why the write is wrapped in try/catch

setItem() can throw a QuotaExceededError when storage is full, and accessing storage can throw a SecurityError when the user or browser has disabled it. Without the try/catch, one failed write would stop every line after it in that script block.

Use cases

  • UI preferences such as theme or a dismissed notice (localStorage).
  • Multi-step form progress within one tab (sessionStorage).
  • Analytics or ad SDKs storing visitor IDs. This is why Web Storage falls under consent rules, just like cookies.

6. IndexedDB

C0004

What it is. IndexedDB is a low-level, asynchronous, transactional database in the browser. It's designed for large amounts of structured data, including files and blobs. Instead of fixed-column tables, it stores JavaScript objects in object stores, indexed by a key. Like other web storage, it follows the same-origin policy.

Key concepts used in the test

  • indexedDB.open(name, version) opens the database, or creates it if it doesn't exist.
  • onupgradeneeded runs when the database is created or the version number increases. It's the only place where you can create object stores.
  • createObjectStore(name, { keyPath: "id" }) creates a store that uses each record's id property as its key.
  • Transaction: all reads and writes run inside one. "readwrite" allows changes.
  • put() inserts the record or replaces it if the key already exists, so reloading the page doesn't throw a duplicate-key error. add() would fail on the second run.
  • db.close(): an open connection blocks deleteDatabase(). Closing it after the transaction lets the clear-storage script delete the database.

Example: read the test record back

const req = indexedDB.open("TestDB", 1);
req.onsuccess = (e) => {
  const db = e.target.result;
  const get = db.transaction("TrackingStore", "readonly")
                .objectStore("TrackingStore").get("TargetingIDB");
  get.onsuccess = () => { console.log(get.result); db.close(); };
};

// Delete the whole database
const del = indexedDB.deleteDatabase("TestDB");
del.onblocked = () => console.warn("Close other tabs using TestDB");

Use cases

  • Offline data for Progressive Web Apps, such as product catalogues or messages.
  • Large or binary data such as images and documents.
  • Third-party SDKs persisting identifiers or event queues. This is why the test ties it to Targeting.

7. Cache Storage (Cache API)

C0005

What it is. Cache Storage stores pairs of HTTP Request and Response objects in named caches. window.caches (a CacheStorage) acts as the directory of those caches. It's mostly used by Service Workers but is also available from normal page scripts. It only works in secure contexts (HTTPS or localhost), and it may be unavailable in some private-browsing modes.

Methods

Method Purpose
caches.open(name) Returns the named cache, creating it if needed
cache.put(request, response) Stores a response for a request URL (used in the test)
caches.match(request) Finds a stored response in any cache
caches.keys() Lists all cache names
caches.delete(name) Deletes a whole named cache

Examples

// What the test writes: a synthetic response for a fake URL
const cache = await caches.open("test-cache-v1");
await cache.put("/social-cache-entry",
  new Response("Social Cache Storage!", { headers: { "Content-Type": "text/plain" } }));

// Read it back
const res = await caches.match("/social-cache-entry");
console.log(await res.text()); // "Social Cache Storage!"

// Remove it
await caches.delete("test-cache-v1");

Use cases

  • Offline app shell: caching HTML, CSS, JavaScript and images.
  • Faster repeat visits with cache-first strategies.
  • Storing JSON API responses for offline use.

8. Service Workers

Not blocked

What it is. A Service Worker is a script that the browser runs in the background, separate from the page. It acts as a network proxy: it can intercept requests, serve responses from Cache Storage, and handle push messages and background sync. Service Workers require a secure context and control only pages within their scope, which by default is the folder the worker file is served from.

Lifecycle

  1. Register: the page calls navigator.serviceWorker.register("/sw.js").
  2. Install: often used to pre-cache files.
  3. Activate: often used to delete old caches.
  4. Fetch: intercepts the network requests of controlled pages.

Example: a minimal /sw.js

self.addEventListener("install", (e) => {
  e.waitUntil(caches.open("app-shell-v1").then(c => c.addAll(["/", "/styles.css"])));
});
self.addEventListener("fetch", (e) => {
  e.respondWith(caches.match(e.request).then(r => r || fetch(e.request)));
});

// Unregister every worker for this origin
const regs = await navigator.serviceWorker.getRegistrations();
await Promise.all(regs.map(r => r.unregister()));

Why it's relevant to consent

Registration in the test is not blocked, and a Service Worker runs outside the page. It can write to Cache Storage or IndexedDB on its own, and OneTrust's text/plain rewriting doesn't apply inside it. If a worker stores non-essential data, either block the registration script with a category class, or check consent before the worker writes anything.

If /sw.js doesn't exist, register() rejects and the .catch() logs a warning instead of failing silently.

10. Consent withdrawal and cleanup

Blocking controls whether a script runs. It doesn't undo what the script has already written. When a user withdraws consent, existing data stays in the browser until it's deleted. A cleanup script needs to handle each storage type separately:

async function clearCategory({ cookies = [], local = [], session = [], dbs = [], cachesToDrop = [] }) {
  cookies.forEach(n => { document.cookie = `${n}=; path=/; max-age=0`; });
  local.forEach(k => localStorage.removeItem(k));
  session.forEach(k => sessionStorage.removeItem(k));
  dbs.forEach(db => indexedDB.deleteDatabase(db));
  if ("caches" in window) await Promise.all(cachesToDrop.map(c => caches.delete(c)));
}

// Example: user withdraws Targeting (C0004)
clearCategory({ cookies: ["TargetingCookie"], local: ["TargetingLocal"], dbs: ["TestDB"] });

A common trigger is OptanonWrapper(), which OneTrust calls on load and whenever consent changes. Check OnetrustActiveGroups there and clear data for any category that is no longer active.

The server-side alternative is the Clear-Site-Data response header. It can clear cookies, storage and cache for the origin in one step, but it clears everything, not a single category.

Limits: JavaScript can't remove HttpOnly cookies or cookies set on another domain, and it can't delete a cookie unless the path and domain match. Third-party vendors' data in their own domains must be handled by those vendors.

11. How to test

  1. Open the page in a fresh private window, or clear site data first (DevTools → Application → Storage → Clear site data).
  2. Before interacting with the banner (opt-in model): only Strictly Necessary data should exist, and none of the test keys should be present.
  3. Accept one category at a time in the Preference Center, and confirm that only that category's items appear.
  4. Accept All: every item in the category table should appear.
  5. Withdraw a category: confirm the script no longer runs on reload, and that the cleanup script removes the existing data.
  6. In the console, check OnetrustActiveGroups and the OptanonConsent cookie's groups= value against what you see in storage.
  7. Test on HTTPS. On plain HTTP, Secure is skipped, and Cache Storage and Service Workers won't work, except on localhost.
Scenario Expected result
No consent (opt-in) No test cookies, Web Storage keys, TestDB or test-cache-v1
Performance only PerformanceCookie + PerformanceLocal
Functional only FunctionalCookie + FunctionalSession (gone after closing the tab)
Targeting only TargetingCookie + TargetingLocal + TestDB
Social Media only SocialCookie + test-cache-v1
Any state Service Worker registration is attempted (unblocked)

12. Full test script

<!-- Helpers: no consent needed (not blocked) -->
<script>
  const isHttps = location.protocol === "https:";
  function setCookie(name, value, maxAge = 31536000) {
    document.cookie = `${name}=${encodeURIComponent(value)}; path=/; max-age=${maxAge}; SameSite=Lax${isHttps ? "; Secure" : ""}`;
  }
  function safeStorage(storage, key, value) {
    try {
      storage.setItem(key, typeof value === "string" ? value : JSON.stringify(value));
    } catch (e) {
      console.warn(`Storage write failed for ${key}:`, e);
    }
  }
  function writeIndexedDB(dbName, storeName, record) {
    if (!("indexedDB" in window)) return;
    const req = indexedDB.open(dbName, 1);
    req.onupgradeneeded = (e) => e.target.result.createObjectStore(storeName, { keyPath: "id" });
    req.onsuccess = (e) => {
      const db = e.target.result;
      const tx = db.transaction(storeName, "readwrite");
      tx.objectStore(storeName).put(record);
      tx.oncomplete = () => db.close();   // free the connection so deletion isn't blocked
      tx.onerror = () => db.close();
    };
    req.onerror = (e) => console.warn("IndexedDB error:", e.target.error);
  }
</script>

<!-- Performance (C0002) -->
<script type="text/plain" class="optanon-category-C0002">
  setCookie("PerformanceCookie", "true");
  safeStorage(localStorage, "PerformanceLocal", "Performance localStorage!");
</script>

<!-- Functional (C0003) -->
<script type="text/plain" class="optanon-category-C0003">
  setCookie("FunctionalCookie", "true");
  safeStorage(sessionStorage, "FunctionalSession", "Functional sessionStorage!");
</script>

<!-- Targeting (C0004) -->
<script type="text/plain" class="optanon-category-C0004">
  setCookie("TargetingCookie", "true");
  safeStorage(localStorage, "TargetingLocal", { id: 123, consent: true });
  writeIndexedDB("TestDB", "TrackingStore", { id: "TargetingIDB", value: "Targeting IndexedDB!" });
</script>

<!-- Social Media (C0005) -->
<script type="text/plain" class="optanon-category-C0005">
  setCookie("SocialCookie", "true");
  if ("caches" in window) {
    caches.open("test-cache-v1")
      .then((cache) => cache.put("/social-cache-entry",
        new Response("Social Cache Storage!", { headers: { "Content-Type": "text/plain" } })))
      .catch((e) => console.warn("Cache write failed:", e));
  }
</script>

<!-- Optional Service Worker -->
<script>
  if ("serviceWorker" in navigator) {
    navigator.serviceWorker.register("/sw.js")
      .catch((e) => console.warn("Service Worker registration failed:", e));
  }
</script>
